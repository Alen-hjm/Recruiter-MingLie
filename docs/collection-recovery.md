# JD 寻访与采集中断恢复

当前本地改动新增普通浏览器执行模式和可选 Scrapling 会话适配器。普通 Dynamic 会话实测在登录前出现空白；后续 Stealthy 会话已通过人工登录后的搜索、单份详情读取和返回验证。翻页与完整 JD 分析尚未实站验收，见 [Scrapling 验收记录](scrapling-validation.md)。

## 启动

在项目虚拟环境安装已有 requirements.txt 依赖，然后运行 `python -m playwright install chromium`。默认 `MINGLIE_SCRAPE_MODE=browser`，使用独立的 `browser_data/user_<id>` 保存人工登录状态。首次使用需要在采集浏览器中登录，最长等待 2 分钟。旧 `cdp`、`stealth`、`basic` 分支仍保留；CDP 是旧手动搜索监听模式，不能当作自动寻访模式。

## 操作

1. 在岗位管理保存岗位名称与 JD。
2. 在简历抓取页选择岗位，点击「从 JD 建议搜索词」，选择或修改关键词。无模型密钥时使用既有规则建议，不能当作模型理解结果。
3. 可勾选「完成采集后按岗位 JD 自动分析」；需要有效的模型配置和 JD。
4. 启动后在采集浏览器登录。系统对账号正常可访问的搜索和简历页面执行操作。
5. 空白页、登录失效、明确验证提示进入「待人工处理」，保留逐条写入的数据。确认恢复访问后，在任务历史点击「重新继续」。

恢复会重新执行原关键词搜索并跳过已保存的简历，并非恢复到平台某个精确页码。平台搜索排序变化可能影响覆盖范围。城市筛选沿用旧实现，尚未验证自动应用；关键词也不等于全部 JD 硬性条件，最终需检查分析依据。

## 状态与边界

- `pending` → `queued` → `running` → `done / attention / error`。
- 每个本地用户同时只启动一个采集任务，避免抢占同一个浏览器目录。
- 已保存的部分简历可直接进入评分，无需等采集全部完成。
- 自动分析启动后记录 `score_task_id`；分析的最终状态在 AI 评分页查看。未实现采集每条即并行评分。
- 服务启动时将遗留运行任务标为待处理，必须手动恢复。当前仍使用进程内线程，只支持单进程部署，不是分布式任务队列。
- 自动评分不再删除低分原始简历。
- 数据库存储无密钥的搜索配置快照；恢复时读取当前模型配置。
- 已引入可选 Scrapling Dynamic/Stealthy 会话；Stealthy 完成两页有限实测，没有引入 n8n。

当前测试覆盖异常保留、恢复去重、重复启动、越权恢复及 JD 自动评分衔接；浏览器检查覆盖登录、任务提示和 JD 建议交互。依赖已安装，Stealthy 已完成有限实站采集；本地 HTTP 模拟模型另行验证评分链路。最新结果与局限见 [验收记录](scrapling-validation.md)。

## 实站诊断记录（2026-10-12）

使用 Codex 内置浏览器打开 `https://h.liepin.com`，首次观察到登录地址 `/account/login?backurl=…`，后续观察到地址为 `about:blank`，截图确认整个页面空白。全程未输入账号或密码；读取当前可用的控制台警告、错误日志返回空列表。

用户随后在另一标签页手动登录。检查该标签页时，首页和「找人」入口均正常显示，确认了登录成功。通过页面上的「找人」链接执行一次点击后，首次观察到 `/search/getConditionItem`，随后标签页变为 `about:blank`。截图请求超时，当前可用的控制台警告、错误日志仍为空。没有填写搜索词、批量读取简历、发送消息或调用模型。

以上为初始诊断历史，不等同于运行项目 Python 采集器的结果。之后的独立浏览器实测与源码发现分别记录于 Scrapling 验收文档和空白页调查文档。
